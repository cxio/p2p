# P2P 基网项目设计

本项目旨在实现一个通用的去中心化P2P节点发现系统，作为P2P世界的网络基础（简称**基网**）。

任意P2P应用或服务的节点都可以连入基网，通过基网发现自己需要的任意应用或服务。各应用或服务也有自己的网络（简称**子网**），如果必要，子网可以复用基网的基础功能（结构化查询、连接维护等）。

> **约定：**
> 为便于表达，在后面的表述中，**服务**也称为**应用**，即提供某种服务的应用。


## 基础网络

### 基本原则

本设计中的节点需遵循如下准则：

- **新身份延迟**：新的基网身份至少 **8** 分钟后才向第三方分享，`10m = Epoch 6m + 容差 2m`。约束可能研磨的 NodeID 的及时扩散能力。
- **适度稳定性**：稳定的节点会获得较长时间的连接，但在适度时长后也会轮换（多样性）。同时稳定的节点也有更高的分享权重。

这样，重新创建 NodeID 的节点需要持续在线一段时间，才有可能被扩散开来，接受连入并充当存储者。

> **实现：**
> 节点缓存曾经连入过的 NodeID，记下首次连入时间。这个时间是延迟和 Epoch 写资格的依据。


### IP 前缀多样性

NodeID 由 SPKIF 决定，但密钥可以任意生成。因此靠 IP 前缀限额约束可接受的身份数量。

- **路由表 k 桶**：同一 IPv4 /16，或同一 IPv6 /32，每个桶最多 **3** 个。
- **k 近邻返回**：同一 IPv4 /24，或同一 IPv6 /48，一次返回最多 **2** 个。
- **登记**：同一 StoreKey 的记录集里，同一 IPv4 /24 或同一 IPv6 /48 最多 **3** 条。

注意，映射在 IPv6 中的 IPv4，用内嵌的 IPv4 计算前缀。

> **实现：**
> 近邻返回按距离从近到远取，同一前缀超过限额即跳过，直到凑满或没有更多候选。


### 工作量认证（连入）

为提升连接成本，抑制攻击者发起大量连接，节点连出前，需要计算工作量：

- 节点发起 TLS 连接请求时，首包 ClientHello 中即包含工作量证明（CH.random）。
- 接受连入的服务端验证工作量，如果合法，返回 ServerHello 包，携带自签名证书和首分享数据（仅支持 TLS 1.3，密文证书和数据）。
- 如果工作量验证失败，返回普通 ServerHello（伪装正常站点，Reality），或简单丢弃（抗 DDoS）。

初始连接工作量认证设计请参阅文档 [工作量认证](1.工作量认证.md)。


### 局部扩展搜索

如果网络规模足够大，大量的有效节点密布，一个历史IP的周围可能就有其它节点在线。因此基于此IP可进行有限范围的扩展扫描发现。或者，如果没有历史IP，用户也可以通过其它渠道，比如社会化方式获取某些地址（含 NodeID），并基于此尝试扩展搜索。

小范围的低频扫描，可能不会触发网络管理方的注意，不过这需要把握尺度，或足够的时间离散性。另外，固定活跃的IP子网也可能是一个切入点。

> **扫描约定：**目标端口统一为 `443 + 8443`，**443** 优先。


### 安全连接

由于P2P网络的节点间不需要信任对方，因此连接仅需采用安全的（TLS），避免第三方的窥探和分析即可。证书采用自签名证书，验证采用 SPKI 指纹（`Hash256(Cert.SPKI)`）核对。

在应用子网内部，节点也会分享、扩散包含 SPKI 指纹在内的节点信息（同类扩散）。


### 连通性级别

- **闪连**：节点与远端仅执行了握手，完成了首包认证和首回包分享。主要用于严酷审查环境下的冷启动。
- **短连**：节点与远端建立了通讯但时间很短，主要为拉取节点完整信息（含 ECHConfig）。通常由闪连衍生，后续扩展而来。
- **长连**：常规的两端正常通讯。由短连的 ECHConfig 支持发展，或正常环境下使用。

闪连也可用于 ECH 场景，此时 ClientHello Inner 的 random 和 Extensions.Message 都不可探测，隐私性更好。`Extensions.Message` 为客户端在 ClientHello 中携带的查询条件，详见 [wTLS](https://github.com/cxio/wtls) 项目。



## 节点信息

### 基网身份

用于连入、路由、首分享和 Kademlia 的 NodeID。对端和路由表看到的是「这是一个基网节点」。

- 版本：  信息格式版本号（uint16）。
- IP:     公网IP，IPv6 格式（IPv4 映射为 IPv6），仅单个地址。
- Port:   基网监听端口，2字节长。
- SPKIF:  公钥信息指纹（自签名证书：`Hash256(Cert.SPKI)`）。
- NATT:   NAT类型（`Public` | `FullC` | `RC` | `P-RC` | `Sym-Like`）。
- Nonce:  随机序列，8字节。也可携带有用信息。

```go
// domainTag 基网域标识：base-net.Identity@v1
// SPKIF     基网密钥的公钥指纹
// Nonce     用于规避工作量特征审查
NodeID = Hash256( domainTag || SPKIF || Nonce )
```

连入之后核验：

1. 证书的 SPKI 指纹与身份里的 SPKIF 一致。
2. 用 `domainTag || SPKIF || Nonce` 重算 NodeID，与对端声明的一致。

验不过则断开。实现上可以要求对端重发一次，只给一次机会。


### 应用记录

用于按「名识」发现节点，出现在 DHT 登记和应用池里。

节点通过名识（`AppID`）表明自己所属的应用。名识采用哈希指纹，如 `Hash(AppName || Version || Salt)`，32 字节。

- 版本：  信息格式版本号（uint16）。
- 名识：  AppID，32 字节。
- IP:     公网IP，编码方式与基网身份相同，仅单个地址。
- Port:   应用端口，2字节长。
- ECHC:   节点的 ECH 配置（ECHConfig，100~200 字节）。
- SPKIF:  应用密钥的公钥指纹。可以与基网身份的 SPKIF 不同。
- NATT:   NAT类型，取值与基网身份相同。
- BaseID: 基网身份，关联到基网。
- Extra:  附加信息，≤64 字节，可选。不同应用的灵活空间。
- Signd： 由上面 SPKI 的私钥签名，锁定各字段。

```go
// domainTag: base-net.Record@v1
// 锁定：字段篡改 => 变签名 => 变 SPKIF => 连接即失败
digest = Hash256( domainTag || Ver || AppID || IP || Port || ECHC || SPKIF || NATT || BaseID || Extra )
Signd = Sign( digest )
```

存储者以及收到分享的节点都核验签名，对不上就丢弃。摘要覆盖记录的全部字段。

DHT 登记时，签名必须有效，记录里的 IP 必须与本次连接的源地址一致。连接上出示的是基网证书，签名用的是应用密钥，两把密钥可以不同。

> **提示：**
> 纯基网节点也可登记为一种应用，以传递完整节点信息。


#### 关于 SPKI

应用密钥和基网密钥可以不同，但因此也会导致计算的 NodeID 不同。如果应用子网希望有自己的身份系统，这提供了一种便利。这不影响用户通过基网 NodeID 在基网找到应用节点。

当然，用户连入目标应用的子网时，使用的就是节点提供的应用 SPKIF 来验证对端了。



### 名识保护

如果已知某节点的 NodeID，可以通过 DHT 结构化查询找到它。但更多的场景，是通过应用的名识找到该应用的任意节点。

此时应用的名识就是一个「数据键」，相对固定，即便可以有不同版本，也有限度。审查者可以针对特定名识的存储位置进行阻击。

保护方式见 [Ploy-名识保护](Ploy-名识保护.md)。



## 节点发现

基网采用两种发现机制：

- DHT 结构化存储和查询（采用 Kademlia 技术）。
- 随机游走的*微广播*自由搜寻。广播扩散跳数严格受限，避免消息洪泛。

这两种方式同时运行，用户可以自由选择使用哪一个或者同时使用。


### DHT 结构化方案

基于 DHT 技术的结构化搜寻，高效且节省。查询是询问者直接向节点请求应用记录，自己提取并逐个尝试，循环迭代。而不是通过广播中转的形式。

在这种模式下，询问发起者掌握所有的主动权，逻辑也更简单。

针对特定的目标应用名识，构造其存储键（`StoreKey`）。

```go
// 详见 Ploy-名识保护.md 文档
StoreKey := Hash256( Seed_e || 名识 || RandX )
```

应用节点会将自己的应用记录存储在与其 StoreKey 临近的节点（NodeID）上。检索这些节点，即可取得目标应用已登记的记录。


#### 注册存储

一个节点注册/更新自己的名识记录，需要存储到与该名识对应 StoreKey 键相邻的节点上。

为避免攻击者连入注册垃圾记录淹没正常节点，存储引入**票券**延迟机制：节点申请写入前需先申领票券，等待一个短暂延时后凭票写入，如果负载较大，可考虑按 IP 前缀限额排序。

> **实现：**
> 延迟时间由存储者根据自身情况灵活决定，通常默认 `30s`（可配置）。

申请者虽然拥有票据，但写入并不必然发生。存储者有权根据自身负载情况或对申请者的评估，决定是否再次延迟（重新发票）。

与自由搜寻的应用池不同，这里只登记提交者**自己的**应用记录，规则：

- 需签名有效，记录中的 IP 与本次连接的源地址一致。
- 同一 StoreKey 同时受前缀限额约束。
- 当前连接上的基网证书可以与记录中签名用的应用密钥不同。


### 自由搜寻方案

与 DHT 一起运行，两种方案由用户自己选择（或同时使用）。这构成了一种有冗余保障的双保险方案。

对于一个节点来说，基本逻辑：

- 接受任意应用（可配置）的记录登记，存入「应用池」。登记要求 IP 与连接源地址一致，并核验签名。
- 应用池里的记录也可以从分享补充，把别人分享的记录合并进来。合并前先核验签名。
- 查询者通过随机游走的方式，向其它节点请求广播发现（较少跳数）。每份查询证明绑定一个入口节点。

搜寻的详细规范请参见文档 [自由搜寻](2.自由搜寻.md)。


#### 应用记录的扩散

基网节点存储的应用记录以名识为键。

```go
// domainTag: base-net.Recognize@v1
Key := Hash256( domainTag || 名识 )
```

信息分享包括两个层级：

- 对名识本身的分享。**注**：节点可以配置自己支持/排除哪些名识。
- 对该名识下部分应用记录的分享。

分享都应是随机的。随着时间的推移，应用记录会在全网的范围内自由扩散……扩散是随机的，扩散的效率（速度和均匀性）无法确定也很难预测。


#### 小网域广播

自由搜寻基于广播查询，范围不宜太宽太远，避免洪泛问题。

查询的广播跳数从**6**开始，最低到**0**终止，扩散率为**4**。因此单个首跳节点向下可扩展到 `4^6 = 4096` 个节点。

除了两个高跳（`6,5`）节点，广播沿途每个节点检查自身是否拥有查询目标，有则返回记录，然后终止转播。回应包按原路径回传，逐级收敛。

广播还有速率约束：初始第 `6`、`5` 跳的包会被严格限制为 `2s/次`，同时所有中转节点都会用令牌桶约束传播速率。入口绑定和转播连接的年龄见 [自由搜寻](2.自由搜寻.md)。


#### 随机游走评估

存储是自由的，节点可以配置支持或不支持某种名识应用，因此查询者可能需要多次迭代，尝试不同的首跳连接。

单首跳的向后扩散最多可达 4096 个节点，合计沿途一共可触及 `5461` 个节点。假设每节点存储的应用记录为**2k**（2048），则理论上一个查询请求最多可触及 `5461*2048 ≈ 1118` 万条记录。排除重叠，也应算是较为充分的筛选规模。

返回响应的节点会及时终止转播，因此实际上的扩散通常不会很远，网络负载也有限。

> **提示：**
> 小众应用如果支持者不多，会需要更多的尝试。



## 应用池

应用池按名识存放应用记录，接受直接登记，也接受分享合并。直接登记要求 IP 与连接源地址一致、签名有效。合并分享前先核验签名，再按稀疏性策略挑选。

接受直连的基网节点需要 NATT 为 `Public` 或 `FullC`，应用记录里的节点则不必如此。记录里的 NATT 为可打洞类型（`RC`, `P-RC`）时，查询者用记录里的 BaseID 到 STUN 服务子网查找它连着的服务节点，再经信令中介打洞。

STUN 服务子网也采用 DHT/Kademlia 技术，且 NodeID 沿用基网身份。服务节点缓存连在它上面的应用节点，所以用应用节点的基网身份（BaseID）可以找到对应的服务节点。

> **区别：**
> DHT 结构化方案也存储应用记录，但两者没有关联（各自独立）。

两个应用节点通过打洞互连所验证的 SPKIF 为其记录中的配置，与其在基网中的 SPKIF 可以不同。


### 配额策略

为避免攻击者通过分享注入自己掌控的不良节点，污染网络，这里采用多维前缀配额（CIDR Diversity Bucketing）策略：

应按 AS 号（自治系统号）、BGP 路由前缀、IPv4 /16、IPv6 /32 分层设限。既防范单点注入，又不会因数值邻近误杀同一 ISP 下的无辜节点。



## 安全性

### 被动分享

节点在对方请求之后才分享自己保存的记录。

客户端连入时，服务端在 TLS 握手回应中附带一批基网身份（首分享）。这是连入的默认行为，也让基网身份扩散得更快。首分享只包含基网身份信息，不是应用记录。应用记录需在完成连接之后，节点主动请求。


### 被动发现

一种极端的隐私保护模式。节点不发出带目标名识的查询，只从应用池的随机分享里识别自己要的应用记录，再去连接。

查询目标不出现在自己发出的包里。这需要足够长的时间，且仅适用于自由搜寻模式。首分享只补充基网身份，不能用来发现应用。



## 技术栈

- **UDP**：采用 QUIC/HTTP3 作为主要的通讯方式。
- **TCP**：适用于 UDP 受限的网络环境，降级采用 HTTP/2 协议。当然也可与 HTTP3 同时运行（由配置决定）。
- **加密**：采用 TLS v1.3 协议，支持后量子加密算法（如 X25519MLKEM768）。
- **消息格式**：采用 Protobuf 进行消息序列化和反序列化。
- **语言**：使用 Go 语言实现，充分利用并发能力。

> **注：**
> 如果应用需要模拟浏览器指纹，可以结合 [uTLS](https://github.com/refraction-networking/utls) 库使用。



## 项目边界

- NAT 内网节点的 NAT 类型判断和存活期探测由项目 `github.com/cxio/stun2` 库支持。
- NAT 内网节点间的打洞连接协助由项目 `github.com/cxio/stun2p` 负责，这是一个实现了 stun2 协议的服务子网。
- 首包工作量认证和首回即分享（ClientHello/ServerHello）由项目 `github.com/cxio/wtls` 实现。


### 关于服务子网

服务子网是一些公共的服务，比如 STUN 探测和打洞服务、数据中转服务等。它们由单独的项目创建，这里无需涉及。



## 附：名词解释

### 基网纯节点

仅实现基网本身的基础功能（包括 drand 随机数中转），没有其它用途的节点，称为基网的**纯节点**。

它们是基网初期扩展的基础（通常成本不高），同时也可能是未来远期整网的融洽成份（或许会有某些必要的进一步工作）。

基网纯节点也可以作为一种特别的“应用”注册自己的名识，然后在应用池中搜寻、连接。

> **设计：**
> 作为本设计中 DHT 结构化存储和查询所必需随机数机制，drand 的中继支持是必须的。


### 基网兼节点

连入基网的应用节点，它们是基网的重要组成部分，不过有*兼职*的观感。

兼职基网不应占用过多的资源。一个应用节点如果从基网获得了需要的入口（进入应用子网），传统上它就可以脱离基网了。但实际上，通过基网搜寻任意节点，可以成为应用子网的一个共享能力（公共锚），比如查找任意服务子网节点、兄弟应用子网跨网联系，以及其它可能的用途等。因此对于应用子网来说，基网不只是帮助找到初始入口，还会有更多可能的价值。

应用子网通常可以保持与基网的持续连接，而且也只有这样，才能充分扩展基网的规模，降低任意应用找到初始入口的门槛。

兼节点不可或缺，它们是完成基网超大规模的主体力量。


### 自由市场

所有参与基网连接的节点的集合（基网纯节点+所有子网节点），统称为节点的*自由市场*。这只是一种逻辑上的称谓，便于表达，不是另有一个独立实体。**基网**的逻辑不包含应用子网自身的功能部分。

自由市场的持续增长可能带来充分的去中心化——以至于应用可能不再需要预置初始的引导节点（远期愿景）。
