# P2P 基网项目设计

本项目旨在实现一个通用的去中心化P2P节点发现系统，作为P2P世界的网络基础（简称**基网**）。

任意P2P应用或服务的节点都可以连入基网，通过基网发现自己需要的任意应用或服务。各应用或服务也有自己的网络（简称**子网**），如果必要，子网可以复用基网的基础功能（结构化查询、连接维护等）。

> **约定：**
> 为便于表达，在后面的表述中，**服务**也称为**应用**，即提供某种服务的应用。


## 基础网络

### 基本原则

本设计中的节点需遵循如下准则：

- **新身份延迟**：对于新的 NodeID 的节点信息，会被延迟至少**6**分钟再分享。约束可能研磨的 NodeID 的及时扩散能力。
- **适度稳定性**：稳定的节点会获得较长时间的连接，但在适度时长后也会轮换（多样性）。同时稳定的节点也有更高的分享权重。

这样，重新创建 NodeID 的节点需要持续在线一段时间，才有可能被扩散开来，接受连入并充当存储者。

> **实现：**
> 节点需要缓存曾经连接过的节点，以记录其 NodeID 的存在性（起点可见）。


### 工作量认证（连入）

为提升连接成本，抑制攻击者发起大量连接，节点连出前，需要计算工作量：

- 节点发起 TLS 连接请求时，首包 ClientHello 中即包含工作量证明（CH.random）。
- 接受连入的服务端验证工作量，如果合法，返回 ServerHello 包，携带自签名证书和首分享数据（仅支持 TLS 1.3，密文证书和数据）。
- 如果工作量验证失败，返回普通 ServerHello（伪装正常站点，Reality），或简单丢弃（抗 DDoS）。

初始连接工作量认证设计请参阅文档 [工作量认证](1.工作量认证.md)。


### 局部扩展搜索

如果网络规模足够大，大量的有效节点密布，一个历史IP的周围可能就有其它节点在线。因此基于此IP可进行有限范围的扩展扫描发现。或者，如果没有历史IP，用户也可以通过其它渠道（比如社会化方式）获取某些地址，并基于此尝试扩展搜索。

小范围的低频扫描，可能不会触发网络管理方的注意，不过这需要把握尺度，或足够的时间离散性。另外，固定活跃的IP子网也可能是一个切入点。

> **扫描约定：**目标端口统一为 `443 + 8443`，**443** 优先。


### 关于无效IP

审查者可以连入网络，收集节点并屏蔽。在无法区分IP实际指向的情况下，大量的无效节点也可以加重审查者负担（特别是P2P场景下），而如果无效节点指向大平台IP（毒IP），无差别封杀则会造成附带伤害……这或许也可以抑制审查的力度。

无效节点来源于登记后下线但尚未移除的节点记录，用户也可以主动配置指向大平台IP的无效地址。前者是常态，而后者通常由现实的严酷程度触发，不属于持久的正常情况。

> **解释：**
> 用附带伤害抑制审查封锁，有伦理上的问题。但终端自然人的权利/公平，也是一个伦理问题。
> 孰轻孰重？或许并没有标准的答案。但至少不算作恶。
>
> 个体是弱者，大平台的各种实力、容忍度或者鲁棒性，明显高于个体。

无效IP混合在分享的节点清单里，对本网络不可用。访问它们相当于可用性测试，无用即弃，不会持续尝试。因此对于极端情况下才可能触发的附带伤害，应当也有限。事无完美，有时候，善是需要一点成本的。

如果环境改善，尽可能少的无效IP可以提升系统效率，这可以促使用户撤销对抗措施，恢复正常的生活。


### 安全连接

由于P2P网络的节点间不需要信任对方，因此连接仅需采用安全的（TLS），避免第三方的窥探和分析即可。证书采用自签名证书，验证采用 SPKI 指纹（`Hash256(Cert.SPKI)`）核对。

在应用子网内部，节点也会分享、扩散包含 SPKI 指纹在内的节点信息（同类扩散）。


### 连通性级别

- **闪连**：节点与远端仅执行了握手，完成了首包认证和首回包分享。主要用于严酷审查环境下的冷启动。
- **短连**：节点与远端建立了通讯但时间很短，主要为拉取节点完整信息（含 ECHConfig）。通常由闪连衍生，后续扩展而来。
- **长连**：常规的两端正常通讯。由短连的 ECHConfig 支持发展，或正常环境下使用。

闪连也可用于 ECH 场景，此时 ClientHello Inner 的 random 和 Extensions.Message 都不可探测，隐私性更好。`Extensions.Message` 为客户端在 ClientHello 中携带的查询条件，详见 [wTLS](https://github.com/cxio/wtls) 项目。



## 节点信息

节点通过**名识**（`AppID`）来表达自己所属的应用。名识需用哈希指纹表示，如 `Hash(AppName || Version || Slat)`。

名识在节点声明自己的身份时提供，它与节点的其它信息一起，共同构成了节点自己的**节点信息**。

- 版本：  信息格式版本号（uint16）。
- 名识：  应用的标识（32 字节）。
- IP:     公网IP，IPv6 格式（IPv4 映射为 IPv6），仅单个地址。
- Port:   应用公网端口，2字节长。
- ECHC:   节点的 ECH 配置（ECHConfig，100~200 字节）。
- SPKIF:  公钥信息指纹（自签名证书：`Hash256(Cert.SPKI)`）。
- NATT:   NAT类型（`Public` | `FullC` | `RC` | `P-RC` | `Sym-Like`）。
- Extra:  额外附加信息，≤64 字节。
- NodeID: 节点的身份ID，由部分字段哈希而来。


### 节点身份&校验

```go
// 节点身份用少数固定字段：
// domainTag 基网域标识：base-net.Identity@v1
// Ver       节点信息版本号
// AppID     所属应用名识
// SPKIF     证书公钥信息指纹
NodeID = Hash256( domainTag || Ver || AppID || SPKIF || Extra )
```

节点接受对端的连接后，会首先请求其节点信息，然后执行验证：

1. 核实其中的 SPKIF 是否与连接时的证书 SPKI 指纹一致。
2. 用版本、名识、SPKIF、Extra 重算 `NodeID`。
3. 若执行 DHT 登记，记录里的 IP 需与本次连接的源地址一致。

若验证不通过，则拒绝进一步的业务通讯或断开连接。**注**：实现中，可能要求对端重新发送信息（给一次纠正机会）。


### 名识保护

如果已知某节点的 NodeID，可以通过 DHT 结构化查询找到它。但更多的场景，是通过应用的名识找到该应用的任意节点。

此时应用的名识就是一个「数据键」，相对固定，即便可以有不同版本，也有限度。因此这可能带来一个问题，如审查者可以针对特定的敏感应用名识进行阻击/屏蔽。

这需要设计某种策略来保护名识的可访问性，详见 [Ploy-名识保护](Ploy-名识保护.md)。



## 节点发现

基网采用两种发现机制：

- DHT 结构化存储和查询（采用 Kademlia 技术）。
- 随机游走的*微广播*自由搜寻。广播扩散跳数严格受限，避免消息洪泛。

这两种方式同时运行，用户可以自由选择使用哪一个或者同时使用。


### DHT 结构化方案

基于 DHT 技术的结构化搜寻，高效且节省。查询是询问者直接请求节点信息，自己提取并逐个尝试，循环迭代。而不是通过广播中转的形式。

在这种模式下，询问发起者掌握所有的主动权，逻辑也更简单。

针对特定的目标应用名识，构造其存储键（`StoreKey`）。

```go
// 详见 Ploy-名识保护.md 文档
StoreKey := Hash256( Seed_e || 名识 || RandX )
```

应用节点会将自己的信息存储在与其 StoreKey 临近的节点（NodeID）上。检索这些节点，即可请求其分享目标应用的登记节点信息。


#### 注册存储

一个节点注册/更新自己的名识记录，需要存储到与该名识对应 StoreKey 键相邻的节点上。

为避免攻击者登记大量垃圾记录淹没正常节点，存储引入**票券**延迟机制：节点申请写入前需先申领票券，等待一个短暂延时后凭票写入。

> **实现：**
> 延迟时间由存储者根据自身情况灵活决定，通常默认 `30s`（可配置）。

申请者虽然拥有票据，但写入并不必然发生。存储者有权根据自身负载情况或对申请者的评估，决定是否再次延迟（重新发票）。

与下面自由搜寻方案中应用池的自由分享不同，这里节点只能登记自己的信息（当前 IP）。


### 自由搜寻方案

与 DHT 一起运行，两种方案由用户自己选择（或同时使用）。这构成了一种有冗余保障的双保险方案。

对于一个节点来说，基本逻辑：

- 接受任意应用节点的信息登记（可配置），将它们存储在一个「应用池」里。
- 应用池的节点信息支持对外分享，以及从分享获得补充。这使得节点的信息可以随机扩散。
- 查询者通过随机游走的方式，向其它节点请求广播发现（较少跳数）。

搜寻的详细规范请参见文档 [自由搜寻](2.自由搜寻.md)。


#### 节点信息的扩散

基网节点存储的应用节点信息以名识为键。

```go
// domainTag: base-net.Recognize@v1
Key := Hash256( domainTag || 名识 )
```

信息分享包括两个层级：

- 对名识本身的分享。**注**：节点可以配置自己支持/排除哪些名识。
- 对该名识下的节点信息集里部分成员的分享。

分享都应是随机的。随着时间的推移，节点信息会在全网的范围内自由扩散……扩散是随机的，扩散的效率（速度和均匀性）无法确定也很难预测。


#### 小网域广播

自由搜寻基于广播查询，范围不宜太宽太远，避免洪泛问题。

查询的广播跳数从**6**开始，最低到**0**终止，扩散率为**4**。因此单个首跳节点向下可扩展到 `4^6 = 4096` 个节点。

除了两个高跳（`6,5`）节点，广播沿途每个节点检查自身是否拥有查询目标，有则返回记录，然后终止转播。回应包按原路径回传，逐级收敛。

广播还有速率约束：初始第 `6`、`5` 跳的包会被严格限制为 `2s/次`，同时所有中转节点都会用令牌桶约束传播速率。


#### 随机游走评估

存储是自由的，节点可以配置支持或不支持某种名识应用，因此查询者可能需要多次迭代，尝试不同的首跳连接。

单首跳的向后扩散最多可达 4096 个节点，合计沿途一共可触及 `5461` 个节点。假设每节点存储的节点信息为**2k**（2048），则理论上一个查询请求最多可触及 `5461*2048 ≈ 1118` 万个节点的信息。排除重叠，也应算是较为充分的筛选规模。

返回响应的节点会及时终止转播，因此实际上的扩散通常不会很远，网络负载也有限。

> **提示：**
> 小众应用如果支持者不多，会需要更多的尝试。



## 应用池

应用池是不同名识对应的节点集合的总集，接受直接的登记和分享合并。

基网节点通常都是 NATT 为 `Public` 或 `FullC` 的类型，以接受外部的直接连入。但被检索/分享的应用池节点则不必如此。如果节点是 NATT 可打洞类型（`RC`, `P-RC`），查询者得到它们的 NodeID 后，就可以在 STUN 服务子网上去找它们，然后通过 STUN 服务节点提供的信令中介完成打洞互连。

STUN 服务子网也采用 DHT/Kademlia 技术，服务节点缓存与之相连的应用节点，因此以应用节点的 NodeID 可以查询其所连接的服务节点。

> **区别：**
> DHT 结构化方案也存储应用节点信息，但两者没有关联（各自独立）。


### 稀疏性策略

应用池中的IP应当遵循**稀疏性**原则，即各个IP之间有适当的距离，避免被攻击者集中注入不良节点信息。

当节点接收对端分享的节点信息时，需要以当前应用池中节点的IP序列为基础，过滤/挑选分享过来的节点信息。这样，攻击者通过分享注入不良节点群的企图就会失去确定性——它们无法预知对端当前的应用池节点状况，进而组织有效的攻击IP集。

> **关于分享：**
> 节点需要对同一请求者限制分享的次数和数量，避免攻击者探测自身应用池状况。
> 节点对分享而来的节点，通常仅需执行半数可达性测试。未测试的部分可包容无效IP/毒IP。

此策略仅适用于自由搜寻方案，DHT 方案为注册存储，无分享补充逻辑。

稀疏性策略用不确定性对抗攻击者IP注入，不过这只是一种缓解措施，攻击危害依然存在。


#### 算法参考

- 将IP转换为整数，计算两个整数的差值。分 IPv4 和 IPv6 两个等级。
- 池中原有的IP不可移除，在一个有序的值集中，新IP只能插入，且需满足前后的距离约束。
- 池中原有的IP间可能不满足距离要求，那是节点自主登记的结果，不受此策略约束。
- 池中的节点按正常的淘汰规则更新（时长、信誉），与插入规则无关。

客观地来看，大网段可以容忍较多的相同子网IP，而小网段容忍的同子网IP就会较少。如果必要，可以分网段设置不同的距离约束。



## 安全性

### 被动分享

节点不应当主动分享自身存储的节点信息，而应该在对方请求后才提供。这更简单也更合理。

客户端在连入服务器时，服务器会在TLS握手回应中附带一批节点信息（首分享）。这既是客户端连入请求的默认逻辑，也强化了节点信息扩散的效率。


### 被动发现

一种极端的隐私保护模式，节点不向外查询需要的名识（敏感应用），只请求分享（随机扩散）以及首分享推来的记录，从中发现自己需要的目标应用的节点，然后建立连接。

这种方式不暴露自己的连接偏好，可以完全隐藏目标（零泄漏），但这需要足够长的时间，且仅适用于自由搜寻模式。



## 技术栈

- **UDP**：采用 QUIC/HTTP3 作为主要的通讯方式。
- **TCP**：适用于 UDP 受限的网络环境，降级采用 HTTP/2 协议。当然也可与 HTTP3 同时运行（由配置决定）。
- **加密**：采用 TLS v1.3 协议，支持后量子加密算法（如 X25519MLKEM768）。
- **消息格式**：采用 Protobuf 进行消息序列化和反序列化。
- **语言**：使用 Go 语言实现，充分利用并发能力。

> **注：**
> 如果应用需要模拟浏览器指纹，可以结合 [uTLS](https://github.com/refraction-networking/utls) 库使用。



## 项目边界

- NAT 内网节点的 NAT 类型判断和存活期探测由项目 `github.com/cxio/stun2` 库支持。
- NAT 内网节点间的打洞连接协助由项目 `github.com/cxio/stun2p` 负责，这是一个实现了 stun2 协议的服务子网。
- 首包工作量认证和首回即分享（ClientHello/ServerHello）由项目 `github.com/cxio/wtls` 实现。


### 关于服务子网

服务子网是一些公共的服务，比如 STUN 探测和打洞服务、数据中转服务等。它们由单独的项目创建，这里无需涉及。



## 附：名词解释

### 基网纯节点

仅实现基网本身的基础功能（包括 drand 随机数中转），没有其它用途的节点，称为基网的**纯节点**。

它们是基网初期扩展的基础（通常成本不高），同时也可能是未来远期整网的融洽成份（或许会有某些必要的进一步工作）。

基网纯节点也可以作为一种特别的“应用”注册自己的名识，然后在应用池中搜寻、连接。

> **设计：**
> 作为本设计中 DHT 结构化存储和查询所必需随机数机制，drand 的中继支持是必须的。


### 基网兼节点

连入基网的应用节点，它们是基网的重要组成部分，不过有*兼职*的观感。

兼职基网不应占用过多的资源。一个应用节点如果从基网获得了需要的入口（进入应用子网），理论上就可以脱离基网了，但还是应该继续保持连接。只有这样，才能充分扩展基网的规模，降低任意应用找到初始入口的门槛。

兼节点不可或缺，它们是完成基网超大规模的中坚力量。


### 自由市场

所有参与基网连接的节点的集合（基网纯节点+所有子网节点），统称为节点的*自由市场*。这只是一种逻辑上的称谓，便于表达，不是另有一个独立实体。**基网**的逻辑不包含应用子网自身的功能部分。

自由市场的持续增长可能带来充分的去中心化——以至于应用可能不再需要预置初始的引导节点（远期愿景）。
