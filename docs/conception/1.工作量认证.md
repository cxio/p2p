# 工作量认证（连入）

节点创建连接前需要先执行一个工作量运算，提升连接成本，优化 P2P 连网机制。

工作量算法基于非对称代价的 `Equi-X` PoW 哈希（抗 GPU/ASIC 矿机），连接方需要付出更多的计算，而接受/验证方的计算成本极低。


## 算法

**通用部分：**

```go
import "github.com/cxio/equix-cgo/puzz"

// 命中率：10%
// 固定配置，针对当前流行PC，100~150ms 级成本。
threshold := puzz.FromProbability(0.1)

// 基础信息：
// 本机只绑定IP（无端口）以避免 Sym NAT 无法通用。因为：
// - 每个 Sym 连出都会分配不同的端口号。
// - 客户端无法预知自己连向另一个节点的端口。
// domainTag 基网的域标签：base-net.Connect@v1
// AppSeed  32字节的基网客户端种子，库升级时可更新
//          默认实现会至少兼容3个旧版的值。
// ClientIP 客户端自己的公网IP
// CH.SNI   ClientHello 上的 SNI，增加熵值
baseInfo := domainTag || AppSeed || ClientIP || CH.SNI
```

**客户端工作量求解：**

```go
// 初始上线时，此集合为空
// 否则已从其它节点接收到分享的节点信息。
Nodes := [...]

if len(Nodes) == 0 {
    // 绑定目标地址（IP:Port）
    // 底层IP数据报中有此信息，可被提取用于审查验证。
    baseInfo = baseInfo || ServAddr
} else {
    // 绑定目标身份（NodeID）
    // 此为应用层信息，无法从底层IP数据报中获取。抗网关审查。
    baseInfo = baseInfo || Nodes[n].NodeID
}

// 求解生成：
// Mac mini Pro M4 单核耗时约 150~200ms
// Timestamp 当前时间戳，按2分钟刻度（单位）计算
// Rand16    16字节随机数，将成为 CH.random 的后半段
// solution  返回的工作量解，2*8 = 16字节。
var Rand16, solution
for {
    // 生成新的 Rand16
    Rand16 = ...
    Timestamp := Now / (time.Minute*2)

    solution, _ = threshold.Try( Hash256(baseInfo || Timestamp || Rand16) )
    if solution != nil {
        break // 找到解
    }
}

// 首包即提供认证信息（16+16=32 字节）。
CH.random = solution || Rand16
```

**服务端验证：**

```go
// 当前时间戳：
// Unix 时间，按 2 分钟刻度分片单位
Timestamp := Now / (time.Minute*2)

// 提取解序列&随机数
solution := CH.random[:16]
Rand16 := CH.random[16:]

// 验证解：
// - 容错当前时间戳（2分钟刻度）的前后一个单位。
// - 容差对端「有/无」自己的节点信息两种情况。
// 性能：
// 多出的几次哈希通常会被提前淘汰（正式验证解之前）。
// 因此依然高效。
// SelfAddr 服务端自己的公网地址（即上面的 ServAddr）。
// NodeID   服务端自己的身份ID，作为节点信息已对外提供。
for n := range [0, -1, 1] {
    // 假设对端已有自己的节点信息
    seed = Hash256( baseInfo || NodeID || Timestamp + n || Rand16 )
    if threshold.Accept( seed, solution ) {
        return true
    }
    // 假设对端为初始上线
    seed = Hash256( baseInfo || SelfAddr || Timestamp + n || Rand16 )
    if threshold.Accept( seed, solution ) {
        return true
    }
}
return false
```


### 安全性

拥有内在确定性的 solution 会削减 CH.random 信息熵，但 solution 本身依然有随机性。

只有在客户端初始上线，没有任何节点信息时，才会使用目标地址（IP:Port）绑定工作量。此时 CH.random 的值可被外部审查者解析计算，验证是否是一个携带工作量的 ClientHello。

审查者成本：

- 需要针对特定目标获取其 `domainTag` 和 `AppSeed`，且 AppSeed 可能随目标应用（库引入）升级而变。
- 实时过滤海量的 QUIC 数据包，因为 ClientHello.random 无特征，所以必须真实验算。
- 求解和验算都抗 GPU/ASIC 加速，必须用 CPU 处理。但验算本身非常高效（单核20~30微秒级）。
- 如果审查者用旁路分析，反馈链路的延迟可能被*首回即分享*的快速反应跳过，双方成功交互。

如果审查者能克服上述成本，则可以拦截只能绑定 `ServAddr` 的没有任何初始节点信息的冷启动节点。对用户/客户端来说，这是一个无法化解的困局。

也因此，客户端需要尽可能避免纯粹的冷启动，比如保留曾经的历史记录、通过社会化方式获取一些当前在线的基网节点信息。如果基网规模足够大，这可能不是一个太难的问题，比如某种开放的公告栏……

> **补充：**
> 因为任意应用都可以借助于基网找到入口节点信息，所以冷启动的问题实际上只会落到基网节点本身。


## 响应分级

发起连接一端的初始 ClientHello 中即包含工作量证明，服务端进行验证。有如下两种情况：

- **非法连接**：无工作量证明或验证未通过，不予理睬或返回普通的 ServerHello（伪装）。
- **正常连接**：工作量证明验证通过，返回的 ServerHello 中包含自签名证书和*首分享*节点集。

> **注意：**
> 可达性测试通过轻量的 Ping/Pong 完成，无法实现验证。
> 可用性测试与可达性不同，此时才需要工作量证明，但计算「更重」。


### 首分享

因为 ClientHello 即包含认证，所以服务端返回的 ServerHello 包中即可包含分享的节点信息。这就是*首回即分享*的快速反应机制。

首分享的数据量遵循原则：*自签名证书 + 节点信息 ≈ 常见网站CA证书链长度*，即节点信息占用证书链中 `n证书-1` 的部分，以使得数据量外观上看不出差别。分享的数据存储在返回的 `ServerHello.EncryptedExtensions.Shared` 字段（详见 [wTLS](https://github.com/cxio/wtls) 项目。

> **实现：**
> 可能需要无效数据 padding 来匹配真实证书链长度，回避包长统计分析。

如果客户端已经获取到服务端的 `ECHConfig` 信息，则可以通过 `ClientHello.Extensions.Message` 来传递目标ID，使得首分享的信息也能支持距离逼近筛选。


#### 节点信息

首分享的节点信息是普通节点信息（见 [设计#节点信息](./0.设计.md)）的精简版本，以适配 ServerHello 包容量的局限：

```go
(2)     版本
(1)     协议 [h2, h3]
(32)    名识，如果是较长明文，应先哈希封装（`SHA2-256`）
(18)    公网地址（IP:Port）
(32)    SPKIF：`Hash256(Cert.SPKI)`
(32)    Proof：工作量证明，用于计算 NodeID
```

> **设计**：即仅包含构造节点身份（`NodeID`）的字段。
> **提示**：量子时代的证书体系（如默克尔树证书MTC）里，可借取的 SH 容量可能更小。

首分享不包含 `ECHConfig`，节点需要正常连接后，通过应用层数据获取节点的 ECHConfig 信息。
