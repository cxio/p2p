# 自由搜寻设计

自由搜寻采用小网域广播方式，尽可能约束消息洪泛的问题。同时，每一个查询请求都需要*工作量证明*，以抑制垃圾查询风暴。

- **扩散规模**：起始跳数 **≤6**，到最终 **0** 值时终止；每级转播最多 **4** 个下级节点。
- **回传策略**：路径节点检索自身缓存，最多提取 **5** 条信息。有结果即终止转播，信息原路回传。
- **隐私保护**：最高两跳（`6,5`）按 **50%** 概率确定递减：递减按正常扩散转播，不减则单节点转播。

## 基本约定

伪代码用 Go 语言高亮，主要为视觉友好，非严格的 Go 语法。其中：

- `(n)` 占用字节数，即 n bytes。
- `[n]` 占用比特位数，即 n bits。
- `(~)` 表示占用不定数量字节数。

字节数和比特位数通常也只是一个示意值，主要表达一种设计意图。


## 搜寻请求

应用节点创建「询问」消息包，其中包含目标名识前缀、加密凭证以及起始跳数。

```go
(2)     Ver:        版本号。
(8)     ID:         标识本次询问，用于回复包中对应其源请求。
(8)     Timestamp:  询问时间戳（Unix，毫秒）。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     KeyPrefix:  目标名识键前缀（≤32）。
(~)     HPKE:       算法标识 + 变长公钥。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    Proof:      工作量证明
(1)     Hops:       剩余跳数，初始值 ≤6，最低到 0。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
以下单向哈希链防止剩余跳数被抬高：
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(20)    WayOn:      路途哈希，逐跳改变。
(20)    WayEnd:     路途终点哈希。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     Extra:      可选，灵活空间，≤64 字节。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
```

询问包为明文。但节点之间的通讯是加密的，避免第三方窥探。

**基本规则：**

- 时间戳与本地时间相差超过 `±2 分钟` 的包会被丢弃。
- 重复的询问包不转发，判定重复用 `Proof`。可能设置条数上限，保新去旧。


### 单向哈希链

询问包携带 40 字节的单向哈希链，避免中继把剩余跳数改大、把广播拉长。

```go
// 查询者：
// 每次发包使用新的 32 字节 Seed，种子不外传。
WayOn = Hash(Seed)
WayEnd = WayOn
for i range Hops+1 {
    WayEnd = Hash(WayEnd)
}

// 接收方先验证，再决定回复或转发。
if Hops > 6 {
    return false
}
tmpOn = WayOn
for i range Hops+1 {
    tmpOn = Hash(tmpOn)
}
if tmpOn != WayEnd {
    return false
}

// Hops == 0：停止。否则转发前只走一步。
if Hops == 0 {
    return
}
Hops = Hops - 1
WayOn = Hash(WayOn)
```

初始跳数并不固定为 **6**，询问者可以根据自身隐私需求调整，但最大值为6。

终点 `WayEnd` 会绑定到 Proof，不良中继可能把跳数多走几步再转发，但只会让广播更短，且只影响当前路径。


### 查询工作量

每个查询都需要完成工作量计算，算法如下（示意）。

**通用部分：**

```go
import "github.com/cxio/equix-cgo/puzz"

// 命中率：6%
// 按当前普通 PC 标定，单核约 500 毫秒。
// 这是一个统一的固定配置，不可修改。
threshold := puzz.FromProbability(0.06)

// 绑定不可变字段。
// domainTag 查询包域标识：base-net.Query@v1
baseInfo := domainTag ||
            Ver ||
            ID ||
            Timestamp ||
            KeyPrefix ||
            HPKE ||
            WayEnd ||
            Extra
```

**每查询求解：**

```go
// 求解：
// Hash256  哈希算法：SHA-256
// Rand16   工作量求解者寻找的16字节随机数，会作为证明的后半段
// solution 一个合法解，2*8 = 16字节
var Rand16, solution
for {
    // 每轮生成新的 Rand16
    Rand16 = ...
    solution, _ := threshold.Try( Hash256(baseInfo || Rand16) )
    if solution != nil {
        break
    }
}
Proof := solution || Rand16
```

**中转/末端验证：**

```go
// 验证解：
// 效率极高，适配现代PC，单核约 30~40 微秒。
Rand16 := Proof[16:]
solution := Proof[:16]
seed := Hash256( baseInfo || Rand16 )

return threshold.Accept( seed, solution )
```

中转节点先检查时间窗、工作量和哈希链，再看自己有没有目标名识的节点信息。


## 响应回复

如果节点查询到结果，创建*回复包*响应。否则在跳数非零时，把跳数减一、`WayOn` 哈希一次后转播。

返回的回复包会按询问广播的原路径逆向回传，逐级收敛回到查询者。

> **设计：**
> 原路回传既可以避免信息洪泛，也可以让询问者不必公开自己的位置（IP）。


### 回复包

```go
(2)     Ver:        版本号。
(8)     ID:         原询问包中的ID，用于匹配上级来源。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     Cipher:     用询问包里的 HPKE 公钥封装。
                    关联数据含询问 ID、Proof、WayOn、HopEnd。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
注：以下信息会用共享密钥加密
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(8)     Timestamp:  回复时间戳（Unix，毫秒）。
(~)     KeyPrefix:  目标名识键前缀，与询问包内的同字段值相同，用于核实确认。
(1)     HopEnd:     抵达时的剩余跳数。
(~)     Nodes:      分享的节点信息集。不超过5条信息。
                    与首分享不同，此节点信息包含完整字段数据。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     Extra:      可选，可能需要的附加信息，≤127 字节。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
```

> **设计：**
> `HopEnd` 放在密文里，避免回复者暴露位置。回传按ID对应即可。


### 末端延时

攻击/审查者可能部署大量监控节点，发现相关请求后立即响应，占据原路回传的头部位置，阻止真实回应。

因此这里设计了一个「末端延时」的策略：

- 对于每一个询问，中转节点记下它抵达时的时间（本地时间）。
- 对于每个回复，至少暂存至其询问下发时间之后至少 **2~3** 秒才向上回传。
- 如果暂存期多个回复抵达，则随机抽选，先抵达的回复没有优先性。

如果回复者的上级节点执行了该约束，则路径中间的节点通常就不再需要延迟了，先抵达的回复先回传。**注**：检查仍需维持。

> **设计：**
> `2~3` 秒的延迟主要考虑节点本地查询所需的消耗。

这样，攻击者如果想要完全阻断回复的抵达，就需要部署十分充足的节点或针对特定询问者围堵才行。


### 回传策略

- 每个中转节点最多向上回传 **16** 个回复包。
- 每个下级节点的回复最多取 **5** 条，以获得路径多样性。

中转节点对下级节点的回复包筛选：

- 如果还在延时期内，则等待汇聚，到点后随机抽选（每节点回复依然不能超过5个）。
- 如果延时期已过，则先到的回复先回传。但最终向上回传的总包数不超过16个。

这样，路径近的回复会先抵达，远的会被淘汰。一个首跳节点返回16个包，若连接4个节点查询，则最多可获得 64 个回复。
