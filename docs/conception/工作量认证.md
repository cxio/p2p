# 工作量认证

节点创建连接前需要先执行一个工作量运算，提升连接成本，防止某些攻击。

工作量算法基于非对称代价的 `Equi-X` PoW 哈希（抗 ASIC 矿机），连接方需要付出更多的计算，而接受/验证方计算成本较低。


## 基本算法

客户端&服务器通用部分：

```go
// @domainTag 某应用的通用标签
// @AppSeed 32字节客户端固定种子，App升级时可能更新。审查应变因子
// @ServAddr 服务端地址，IP:Port格式字符串
// @ClientIP 客户端公网IP地址（无端口）
// @Timestamp 当前时间戳，容许 `±5分钟` 的误差
// @ECH.SNI 设置到 ClientHello 上的 SNI 信息，可增加熵值
// @Rand16 16字节随机数，将成为 CH.random 的后半段
challengeSeed := Hash256( domainTag || AppSeed || ServAddr || ClientIP || Timestamp || ECH.SNI || Rand16 )
```


### 客户端运算

```go
// 过程：
// appNonce 作为内部 nonce 不变，通过调整 Rand16 来改变 challengeSeed 求解 solution。
// @appNonce: uint64 随机数，客户端内置，升级时更新。审查应对因子2。
// @solution 返回的8个哈希索引（每索引2字节），共16字节。
for {
    challengeSeed = Hash256( ... )
    solution, err := equix.Solve(challengeSeed, appNonce)
}

// 首包即提供认证信息（16+16=32 字节）。
CH.random = solution || Rand16
```


### 服务端验证

```go
// 提取随机数 Rand16，计算 challengeSeed
Rand16 := CH.random[16:]
challengeSeed := Hash256( ... )

// 提取解序列，验证解合法。
solution := CH.random[:16]
isValid := equix.Verify(challengeSeed, solution, appNonce)
```


### 安全性

内在确定性的 solution 会削减 CH.random 信息熵，但 solution 本身依然有随机性。

为避免中间审查者通过验证 CH.random 特征来发现这是一个工作量认证的连接请求，客户端可以内置多个 appNonce，验证时任一符合皆可。这也是App升级后的自然状态。

对于中间审查者来说，可核查的只有 CH.random 一个目标，而其外观与普通的 TLS 没有任何区别。在海量的 TLS 连接请求中，这种抽查的费效比应该很低，尤其是在 P2P 这种自由连接且动态变化频繁的场景下。


### 价值

这是一种首包即认证的工作模式，如果连接请求无法被即时阻断，结合 ServerHello 首回即分享的设计，对 P2P 网络很有价值。

实际上，这也创建了一种开放式认证：任何应用都可以基于自身的 domainTag 来实现本类节点的识别。


## 响应分级

发起连接一端的初始 ClientHello 中即包含工作量证明，服务端进行验证。有如下两种情况：

- **非法连接**：无工作量证明或验证未通过，返回普通的 ServerHello（含证书链），或不予理睬（类似无效节点）。
- **正常连接**：工作量证明验证通过，返回的 ServerHello 中包含自签名证书和*首分享*节点集。

> **注：**
> 可达性测试也可以通过更轻量的 Ping/Pong 循环完成。


### 首分享

因为 ClientHello 即包含认证，所以服务端返回的 ServerHello 包中即可包含分享的节点信息。

分享的节点信息数据量遵循原则：*自签名证书 + 节点信息 ≈ 常见Web网站CA证书链长度范围*，即首分享的节点信息占用证书链中 `n证书-1` 的部分，使得外观数据量上看不出差别。

分享的节点信息存储在返回的 `EncryptedExtensions.Shared` 部分，`Shared` 为自定义字段。

这是一种*快速反应机制*，中间审查者需要反应极快，才可能对首个回包进行阻断。而 CH.random 携带的工作量只能通过在海量的 TLS 首包中无差别抽查才能发现，稍有延迟，首个回包可能就已经抵达请求源，完成了节点分享。

为使得首分享的节点信息也支持距离逼近筛选，ClientHello 包中的 *key_share fallback X25519* 会被定制使用（详见 [wTLS](https://github.com/cxio/wtls)），示意伪代码如下：

```go
// 序列末尾最后一位标注检索类别：
// - 置位：检索名识记录，用名识存储键（StoreKey）进行距离对比。
// - 清位：检索基网节点，用节点ID（PeerID）进行距离逼近查找。
StoreKey2 = StoreKey | 0x1  // 置位，检索名识记录
// or
PeerID2 = PeerID & 0xFE     // 清位，查找其它基网节点

// 取 PeerID 或 StoreKey 完整 32 字节
CH.Extension.key_share[X25519] = PeerID2 or StoreKey2
```

注意，连入基网的节点都是基网节点，它可能需要查找与其ID距离临近的其它基网节点，建立稳定的连接。这是正常的基网节点组网逻辑，此时远端分享者只需要逼近查找即可。

如果节点想查找某个特定应用的节点，需要通过名识存储键检索，此时通常需要键名严格匹配。因为键末尾一位用于标注检索类别，所以该位失效。这并不会成为一个问题，逻辑上，仅键名前段局部相等的模糊匹配也是可以的，只要前段足够长（255有效位），就不会对检索的结果造成影响。


### 关于 ECH

如果没有 ECH，客户端新建连接时的 ClientHello.SNI 应当是有效的才好，否则审查者可以通过快速查询 SNI 的有效性，从而辨别出该请求。

通过首分享，节点信息中包含了 ECHConfig，客户端新建连接时，ClientHello.SNI 就可以名正言顺的虚假，审查者也就没有了判断的依据。但极端情况下，ECH 可能被系统性一刀切封杀。因此 ECH 是可选的，但也是有价值的。
