# 功能性封面查询调度

此为客户端「自由搜寻」模式下的通用策略：利用日常维护查询与生态探测使查询流多样化，降低审查者对单一目标的实时聚焦能力。


## 背景知识

自由搜寻的询问包 `KeyPrefix` 字段对中继路径明文可见，首跳同时可见查询者 IP。审查者运营基网中继节点即可被动收集「IP <==> 兴趣」关联。

如果一个节点在时间窗口内仅发出一种名识键的查询，锁定成本趋近于零。而如果该节点的查询流呈现**多样化的长尾分布**，单键聚焦度则可能降至自动化筛选阈值之下。


## 实现策略

**节点应在自由搜寻时，将自身真实需求的查询与日常维护查询、生态探测查询穿插轮转。**


### 一、利用既有的维护查询作为天然封面

基网节点运行的以下几类查询在面向上与敏感查询**协议同构、格式不可区分**且**始终存在**，构成天然的背景杂讯：

- DHT 路由维护（NodeID 近邻查找）
- 服务子网列表刷新（STUN、Relay 等）
- 已接入应用子网的周期性邻居探测

正确操作是：*将各种查询穿插编排在一个统一的发送轮转里*。而非将维护查询集中发出、敏感查询单独发送。


### 二、生态探测扩展画像宽度（填充式封面）

在真实需求之外，节点周期性加入**目前并不使用的流行应用名识或服务键**，扩展查询序列的键多样性。

这些查询可能是合理的：建立未来可用应用的「预连接池」，兼作对网络存活性与规模的探测取样。非纯噪声，且不影响任何合法节点的行为。


### 三、键前缀匹配的自然分组（键级不可区分）

如果需要更高的模糊程度，可以对目标名识键取更短的前缀。相同的前缀自然构成分组，使得目标更难以精确定位。

此时审查者观察到的不是具体名识键而是包含众多类别的组键，查询末端的客户端会根据「键均衡」返回随机信息，确保结果**宽阔且频率均衡**。审查者仅能看到模糊的表面，无法从中聚焦。


## 调度器规格（客户端实现指导）

### 环表数据结构

调度器维护一张逻辑环形表，每一行描述一个封面行条目：

| 字段 | 说明 |
|------|------|
| `KeyPrefix` | 目标名识键前缀 |
| `required` | 是否必需（true：周期性必发；false：可选，填充画像宽度） |
| `interval` | 期望轮转间隔（可缺省） |


### 环表初始内容（预置、应用默认携带）

**必需行**（系统保证的基础嗡嗡声）：

| Key | 来源 |
|-----|------|
| 基网路由刷新键 | NodeID 近邻查找，无具体名识 |
| STUN 服务子网键 | `Hash256(domainTag \|\| "stun-service")` |
| Relay 服务子网键 | `Hash256(domainTag \|\| "relay-service")` |

> **注**：domainTag: `base-net.Subnet@v1`

**可选行**（出厂预置或热更新下发）：

| Key | 来源 |
|-----|------|
| 一组热门应用的键（如即时通讯、文件分享等主流名识） | 生态统计数据 |
| 一组中频应用的键 | 可动态从网络查询结果中自学习更新 |

**实际行**（用户真实需求）：

| Key | 来源 |
|-----|------|
| 用户使用的各应用名识键 | 由应用层注入 |


### 约束

- 环表内容的注入从应用上线开始即定型：初始必包含 STUN/Relay/基网三行。
- 用户敏感行加入后，**不改变调度器结构，仅在环表中增加一行，其在旋转中的天然位置由插入时机自然确定**。
- 可选行的初始集由应用二进制预置，随应用升级更新，或由配置通道下发。
- 不对特定首跳对端连续发送多轮，防止该对端在短时间窗口内收集到过于集中的键信息。


## 成效评估

- **效果**：单一目标丧失可聚焦性，干净画像很难完成，「观察→判定→自动封锁」的审查流水线可能失效。
- **不足**：对拥有**长周期内离线统计能力**的审查者，频率分析仍可能推断偏好。


### 优点

- 本策略不增查询延迟，不增迭代次数，只编排顺序。
- 由于 STUN、Relay 等在协议面上与任何应用子网的发现完全同构，基础嗡嗡声天然具备。
- 如果基网规模普及，大量常见应用也是相同逻辑的杂讯，保护性同步上升。
