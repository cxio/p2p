# P2P 基网项目设计

本项目旨在实现一个通用的去中心化P2P节点发现系统，作为P2P世界的网络基础（简称**基网**）。

任意P2P应用或服务的节点都可以连入基网，通过基网发现自己需要的任意应用或服务。各应用或服务也有自己的网络（简称**子网**），如果必要，子网可以复用基网的基础功能（结构化查询、连接维护等）。

> **约定：**
> 为便于表达，在后面的表述中，**服务**也称为**应用**，即提供某种服务的应用。


## 基础网络

### 基本原则

本设计中的节点需遵循如下准则：

- **新身份延迟**：对于新的 NodeID 的节点信息，会被延迟至少**5**分钟再分享。
- **稳定性优先**：连接稳定的节点会有更高的分享权重，间接约束全新上线节点的身份扩散。

这样，重新创建 NodeID 的节点需要持续在线一段时间，才有资格被扩散开来，接受别的节点的连入，充当存储者。

> **实现：**
> 节点需要缓存曾经连接过的节点，如果新连入的 NodeID 在该缓存中，则表示其身份早已创建，5分钟的延时不再适用。
> 缓存的时间或数量由客户端/用户自由配置，这只是一种概略的限制，无需100%精确。
>
> 作为新节点自身，需要尽可能高频地连接其它节点，呈现身份时间起点。但同时也需要平衡连接稳定性权重。


### 初始工作量认证

为提升连接成本，抑制攻击者发起大量连接，这里设计了工作量认证机制：

- 节点发起 TLS 连接请求时，首包 ClientHello 中即需包含工作量证明。
- 接受连入的服务端验证工作量，如果合法，返回 ServerHello 包，携带自签名证书和首分享数据。
- 如果工作量验证失败，返回伪装的普通 ServerHello（包含CA证书链），或简单丢弃。

初始连接工作量认证详情请参阅文档 [工作量认证](工作量认证.md)。


### 暴力发现的可能

P2P世界中一个久未解决的难题，是节点上线时的初始引导节点中心化的问题：引导节点一旦被封锁……

本设计有一个思考：*在不追求及时性的前提下，如果目标网络足够大，遍历全网 IPv4 地址，暴力发现初始的入口节点是否可行？*

基网作为一个P2P世界的基础设施，如果大量的应用支持并加入进来，它们作为基网兼节点充实基网规模……一个百万级连接的网络是可能的。在此规模下，暴力发现就有了可行性。

作为一种优化，历史IP可能是有用的：如果节点只是切换到了它附近的位置，以历史IP为原点的小范围搜寻会很高效。另外，固定活跃的IP子网也是一个可优化的方向。

> **提示：**
> 如果有必要，用户使用一台小设备挂机，持续探测……
> 在极端情况下，小时级的成本是可接受的——因为一旦接入，就基本上万事大吉。

注意，暴力发现是最后的方式，探测频率应当有所节制：

1. 非高频。
2. 非固定频率（间隔有抖动）。

**约定**：暴力发现基于一个默认前提，所有的目标端口统一为：`443 + 8443`，**443** 优先。


### 关于无效IP

审查者也可能连入网络，然后收集节点并屏蔽。在无法区分IP实际指向的情况下，大量的无效节点可以加重审查者负担，而如果无效节点指向大平台IP，封杀则会造成附带伤害……这或许也可以抑制审查的力度。

无效节点信息来源于登记后下线但尚未移除的节点记录，或者用户主动配置的「毒IP」（大平台IP）。后者是客户端用户自主的选择，无法阻止，但这通常是由现实的严酷程度演生而来，不应该是常态。

无效IP混合在分享的节点清单里，对本网络不可用，但我们需要适度的容忍它们。

> **说明：**
> 对无效IP的访问相当于可用性测试，不可用即放弃（不会持续尝试），因此负面影响有限。


### 安全连接

由于P2P网络的节点间不需要信任对方，因此连接仅需采用安全连接（TLS），避免第三方的窥探和分析即可。证书采用自签名证书，验证采用 SPKI 指纹（`Hash256(Cert.SPKI)`）核对。

在应用子网内部，节点也会分享、扩散包含 SPKI 指纹在内的节点信息（同类扩散）。


### 连通性级别

- **闪连**：节点与远端仅执行了握手，完成了首包认证和首回包分享。主要用于严酷审查环境下的冷启动。
- **短连**：节点与远端建立了通讯但时间很短，主要为拉取节点完整信息（含 ECHConfig）。通常由闪连衍生，后续扩展而来。
- **长连**：常规的两端正常通讯。由短连的 ECHConfig 支持发展，或正常环境下使用。

闪连也可用于 ECH 场景，此时 ClientHello Inner 的 random 和 Extensions.Message 不可探测，隐私性更好。



## 节点信息

节点通过**名识**（`AppID`）来表达自己所属的应用。名识通常为「应用名称 + 版本」，但也可能用哈希指纹表示，如 `Hash(AppName || Version || Slat)`。

名识在节点声明自己的身份时提供，它与节点的其它信息一起，共同构成了节点自己的**节点信息**。

- 版本： 信息格式版本号（uint16）。
- 名识： 应用的标识（≤64 字节）。
- 协议： 节点支持的协议，`h3` 或 `h2`，或两者同时支持。
- 地址： 公网地址（IP:Port），IPv6 格式（IPv4 映射为 IPv6），仅单个地址。
- ECHC： 节点的 ECH 配置（ECHConfig，100~200 字节）。
- SPKIF：公钥信息指纹（自签名证书：`Hash256(Cert.SPKI)`）。
- NATT： NAT类型（`Public` | `FullC` | `RC` | `P-RC` | `Sym-Like`），可选（仅 `h3` 时需要）。
- Proof：工作量证明（`Equi-X`），32字节。
- NodeID：节点的身份ID，`Hash256(Proof)`。
- Extra：应用自定义信息（≤64 字节），可选。


### 设计要点

- 通讯协议采用 HTTP/2 或 HTTP/3 以模拟浏览器流量，避免严苛审查环境下的连接问题。TCP（`h2`）是 UDP（`h3`）不可用时的降级备选。
- 节点身份ID是 `Proof` 的哈希摘要，Proof 的成本在秒级。这对正常节点单次运算问题不大，但对研磨 NodeID 则成本很高。
- `Proof` 会关联部分字段，包含公网IP，因此 NodeID 不是持久的身份表达。如果节点想要持久信誉或跨应用一致性，可用 SPKIF：复用即保持一致，独立则天然隔离。


### 身份工作量

节点构造身份有工作量要求，这可以抑制攻击者短时间内创建大量满足某种特征的节点（研磨 NodeID），比如日蚀攻击：针对目标ID创建与其临近的节点ID。

**Proof**采用抗 GPU/ASIC 的 `Equi-X` 哈希算法：

```go
import "github.com/cxio/equix-cgo/puzz"

// 命中率：1%
// 固定配置，针对当前流行PC，秒级成本。
threshold := puzz.FromProbability(0.01)

// 种子固定信息：
// 与节点信息中的部分字段对应（绑定）。
// 注意只绑定IP，不含端口。
// domainTag 固定的基网域标识
// Ver       节点信息格式版本号
// Proto     节点支持的协议（h3|h2|h3,h2）
// AppID     应用名识（标识）
// IP        节点的公网 IP（纯 IPv6 仅取 /64 前缀）
// SPKIF     证书公钥信息指纹
baseInfo := domainTag || Ver || Proto || AppID || IP || SPKIF
```

**客户端工作量计算：**

```go
// 求解生成：
// Mac mini Pro M4 单核耗时约 1~2s
// Rand16   16字节随机数，将作为证明的后半段
// solution 一个合法解，2*8 = 16字节
var Rand16, solution, err
for {
    // 生成新的 Rand16
    Rand16 = ...
    solution, err = threshold.Try( Hash256(baseInfo || Rand16) )
    if solution != nil {
        break // 找到解
    }
}
Proof := solution || Rand16
NodeID := Hash256( Proof )
```

**节点验证对端身份：**

```go
// 高效验证：
// 非对称代价，比求解轻量数万分之一（几十微秒）。
Rand16 := Proof[16:]
seed := Hash256( baseInfo || Rand16 )

solution := Proof[:16]
return threshold.Accept(seed, solution)
```


### 身份校验

节点接受对端的连接后，会首先请求其节点信息，然后执行验证：

1. 核实其中的 SPKIF 是否与连接时的证书 SPKI 指纹一致。
2. 核对 `Hash256( Proof ) == NodeID`。
3. 验证工作量证明（`Proof`）里的解是否合法。

若验证不通过，则拒绝进一步的业务通讯或断开连接。**注：**实际实现中，可能要求对端重新发送信息（给一次纠正机会）。


### 名识保护

应用的名识是固定的，以便于识别查找，即便是多个，也有限度。因此这可能是一个问题，比如审查者可以针对特定的敏感应用名识进行阻击/屏蔽。

这需要设计某种策略来保护名识的可访问性，详见 [Ploy-名识保护](Ploy-名识保护.md)。



## 节点发现

基网采用两种发现机制：

- DHT 结构化存储和查询（采用 Kademlia 技术）。
- 随机游走的*微广播*自由搜寻。广播扩散跳数严格受限，避免消息洪泛。


### DHT 结构化方案

基于 DHT 技术的结构化搜寻，高效且节省。查询是询问者直接请求节点信息，自己提取并逐个尝试，循环迭代。而不是通过广播中转的形式。

在这种模式下，询问发起者掌握所有的主动权，逻辑也更简单。

针对特定的目标应用名识，构造其存储键（`StoreKey`）。

```go
// 详见 Ploy-名识保护.md 文档
StoreKey := Hash256( Seed_e || 名识 || RandX )
```

应用节点会将自己的信息存储在与其 StoreKey 临近的节点（NodeID）上。检索这些节点，即可请求其分享目标应用的登记节点信息。


#### 注册存储

一个节点注册/更新自己的名识记录，需要存储到与该名识对应 StoreKey 键相邻的节点上。

为避免攻击者登记大量垃圾记录淹没正常节点，存储引入**票券**延迟机制：节点申请写入前需先申领票券，等待一个短暂延时后凭票写入。

> **实现：**
> 延迟时间由存储者根据自身情况灵活决定，通常默认 `30s`（可配置）。

申请者虽然拥有票据，但写入并不必然发生。存储者有权根据自身负载情况或对申请者的评估，决定是否再次延迟（重新发票）。

> **真实性：**
> 节点只能登记自己的节点信息，而其中包含的 NodeID、名识、SPKIF 等是可以验证的。


### 自由搜寻方案

作为 DHT 不可用或用户自己的选择，这是一个备选的兜底保障方案。

基本逻辑：

- 一个节点接受任意（可配置）应用节点的信息登记，将它们存储在一个「应用池」里。
- 应用池的节点信息支持对外分享，以及通过分享来补充。这使得节点的信息可以「随机扩散」。
- 一个节点通过随机游走的方式，向其它节点请求广播发现（极少跳数，微风暴）。

> **设计：**
> 应用池节点信息的分享为被动模式，只在收到请求后分享。


#### 节点信息的扩散

基网节点存储的应用节点信息以名识为键。

```go
Key := Hash256( domainTag || 名识 )
```

信息分享包括两个层级：

- 对名识本身的分享。**注**：节点可以配置自己支持/排除哪些名识。
- 对该名识下的节点信息集里部分成员的分享。

分享都应是随机的。随着时间的推移，节点信息会在全网的范围内自由扩散……扩散是随机的，扩散的效率（速度和均匀性）无法确定也很难预测。


#### 有限成本的微广播

自由搜寻基于广播查询，需要中转逻辑。广播的范围如果太宽太远，会造成网络数据包洪泛的问题。

因此这里设计的转播跳数极为有限，仅**3**跳，严格约束查询请求的放大影响。

- 查询请求的初始跳数为 `2`，每一次转播跳数减一，至跳数为 `0`，即不再转播。
- 中转者**不检查**自身是否满足查询条件，仅广播路径的末端检查自身存储：是否有目标名识的节点信息？
- 每一个查询请求都需要包含*工作量证明*，抑制攻击者的垃圾查询风暴。

- 对于首跳接收者节点来说，同一查询者的请求频率最高为 `4s/次`。严格约束请求数量。
- 每次转发最多**8**个下级节点，即每请求的扩散率（单首跳）：`8*8 = 64`。
- 每个末端节点最多返回**8**条记录，回应包按原路径全量回传。即每请求响应记录最多：`64*8 = 512`。

中转节点负载自适应，负载过大时延迟转播：溢出丢弃（弃新保旧）。

末端节点选取节点信息时，按「*键均衡*」随机筛选（而不是按记录），避免大众应用淹没小众应用。


#### 随机游走评估

存储是自由的，末端节点未必支持查询的目标名识，因此没有信息返回。查询者可能需要不断迭代、不断更新所连接的节点，一轮又一轮……

如果末端节点存储的节点信息总共为**4k**（4096），按上面的广播扩散模型：`64*4096 = 262144`，理论上每一个请求可以触及 26 万个节点信息。

如果一个查询者平均连接**8**个节点，一轮请求即可触及（筛选）`262144*8 = 2097152` 约 200 万个节点。当然，这种触及会有大量重复。

> **提示：**
> 小众应用节点数量不多（可见性不足），查询通常需要更多的时间。



## 应用池

应用池是不同名识对应的节点集合的总集。

基网节点通常都是 NATT 为 `Public` 或 `FullC` 的类型，以接受外部的直接连入。但被检索/分享的应用池节点则不必如此。如果节点是 NATT 可打洞类型（`RC`, `P-RC`），查询者得到它们的 NodeID 后，就可以在 STUN 服务子网上去找它们，然后通过 STUN 服务节点提供的信令中介完成打洞互连。

同一应用的节点间没有任何关联，以 NodeID 为目标的 DHT 查询匹配的 STUN 服务节点也各异，因此攻击者很难通过封锁某个 STUN 服务节点来阻止某一应用的节点间组网。

> **提示：**
> STUN 服务子网也采用类似 DHT/Kademlia 的技术。

> **设计：**
> 以上规则也适用于 DHT 结构化查询中存储的应用节点信息。


### 稀疏性策略

应用池中的IP应当遵循**稀疏性**原则，即各个IP之间有适当的距离，避免被攻击者集中注入不良节点信息。

当节点接收对端分享的节点信息时，需要以当前应用池中节点的IP序列为基础，过滤/挑选分享过来的节点信息。这样，攻击者通过分享注入不良节点群的企图就会失去确定性——它们无法预知对端当前的应用池节点状况，进而组织有效的攻击IP集。

> **分享频率：**
> 节点需要对同一请求者限制分享的次数和数量，避免攻击者探测自身应用池状况。

稀疏性策略用不确定性对抗攻击者IP注入，不过这只是一种缓解措施，攻击危害依然存在。

> **注：**
> 此策略仅适用自由搜寻方案（DHT 方案仅有注册存储，无分享补充逻辑）。


#### 算法参考

- 将IP转换为整数，计算两个整数的差值。分 IPv4 和 IPv6 两个等级。
- 池中原有的IP不可移除，在一个有序的值集中，新IP只能插入，且需满足前后的距离约束。
- 池中原有的IP间可能不满足距离要求，那是节点自主登记插入的结果，不影响。

客观地来看，大网段可以容忍较多的相同子网IP，而小网段容忍的同子网IP就会较少。如果必要，可以分网段设置不同的距离约束。



## 安全性

### 初始节点植入

初始节点可以由应用内置或用户配置导入。如果两种方式都失效，则尝试暴力发现的方式遍历IPv4地址进行搜寻。

在网络发展的初期，基网规模不大，在App中预先植入一些已知的基网节点是必要的。当网络发展到一定规模，暴力发现的成本不再高不可攀，这些预植入的节点信息（可保留）就无关紧要了。


### 被动分享

节点不应当主动分享自身存储的节点信息，而应该在对方请求后才提供。这更简单也更合理。

客户端在连入服务器时，服务器会在TLS握手回应中附带一批节点信息（首分享）。这既是客户端连入请求的默认逻辑，也强化了节点信息扩散的效率。


### 被动发现

一种极端的隐私保护模式，节点不向外查询需要的名识（敏感应用），只请求分享（随机扩散）以及首分享推来的记录，从中发现自己需要的目标应用的节点，然后建立连接。

这种方式不暴露自己的连接偏好，可以完全隐藏目标（零泄漏），但这需要足够长的时间，且仅适用于自由搜寻模式。



## 技术栈

- **UDP**：采用 QUIC/HTTP3 作为主要的通讯方式。
- **TCP**：适用于 UDP 受限的网络环境，降级采用 HTTP/2 协议。当然也可与 HTTP3 同时运行（由配置决定）。
- **加密**：采用 TLS v1.3 协议，支持后量子加密算法（如 X25519MLKEM768）。
- **消息格式**：采用 Protobuf 进行消息序列化和反序列化。
- **语言**：使用 Go 语言实现，充分利用并发能力。



## 项目边界

- NAT 内网节点的 NAT 类型判断和存活期探测由项目 `github.com/cxio/stun2` 库支持。
- NAT 内网节点间的打洞连接协助由项目 `github.com/cxio/stun2p` 负责，这是一个实现了 stun2 协议的服务子网。
- 首包工作量认证和首回即分享（ClientHello/ServerHello）由项目 `github.com/cxio/wtls` 实现。


### 关于服务子网

服务子网是一些公共的服务，比如 STUN 探测和打洞服务、数据中转服务等。它们由单独的项目创建，这里无需涉及。



## 附：名词解释

### 基网纯节点

仅实现基网本身的功能，没有任何其它用途的节点，称为基网的**纯节点**。

它们是基网初期扩展的基础（通常成本很低），同时也可能是未来远期整网的融洽成份（或许会有某些必要的进一步工作）。

基网纯节点也可以作为一种特别的“应用”注册自己的名识，然后在应用池中搜寻、连接。


### 基网兼节点

连入基网的应用节点，它们是基网的重要组成部分，不过有*兼职*的观感。

兼职基网并不会占用过多资源。一个应用节点如果从基网获得了需要的入口（进入应用子网），理论上就可以脱离基网了，但还是应该继续保持连接。只有这样，才能充分扩展基网的规模，让无需中心的暴力发现成为可能。

兼节点不可或缺！它们是基网百万级以上规模的关键力量。


### 自由市场

所有参与基网连接的节点的集合（基网纯节点+所有子网节点），统称为节点的*自由市场*。这只是一种逻辑上的称谓，便于表达，不是另有一个独立实体。**基网**的逻辑不包含应用子网自身的功能部分。

自由市场的持续增长可能带来真正的去中心化——完全的无中心，以至于不需要预置的初始引导节点。
