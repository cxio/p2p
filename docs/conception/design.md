# P2P 基网项目设计

本项目旨在实现一个通用的去中心化P2P节点发现系统，作为P2P世界的网络基础（简称**基网**）。

任意P2P应用或服务的节点都可以连入基网，通过基网发现自己需要的任意应用或服务。各应用或服务也有自己的网络（简称**子网**），如果必要，子网可以复用基网的基础功能（结构化查询、连接维护等）。

> **约定：**
> 为便于表达，在后面的表述中，**服务**也称为**应用**，即提供某种服务的应用。


## 节点信息

节点通过**名识**来表达自己所属的应用。名识通常为“应用名称 + 版本”，但也可能采用名称的哈希指纹来表达，如 `Hash(AppName || Version || Slat)`。

名识在节点声明自己的身份时提供，它与节点的网络信息组合，构成了节点自身的**节点信息**。

- 版本：信息格式版本号（uint16）。
- 名识：应用的标识，最长不超过64字节。
- 协议：节点支持的协议，`h3` 或 `h2`，或两者同时支持。
- 地址：公网地址（IP:Port），IPv6 格式（IPv4 映射为 IPv6），仅单个地址。
- ECHC：节点的 ECH 配置（ECHConfig，100~200 字节）。
- SPKIF：自签名证书 SPKI 的哈希指纹：`Hash256(Cert.SPKI)`。
- NATT：NAT类型（`Public` | `FullC` | `RC` | `P-RC` | `Sym-Like`），可选（仅 `h3` 时需要）。
- Extra：应用自定义信息（≤64 字节），可选。
- Timestamp：节点信息的发布时间（Unix，秒），由发布者在求解工作量时确定。
- Proof：工作量证明（`Equi-X`），抑制大规模节点生成。32字节。
- PeerID：节点的身份ID，`Hash256(Proof)`。

> **设计：**
> 通讯协议采用 HTTP/2 或 HTTP/3 以模拟浏览器流量，避免严苛审查环境下的连接问题。
> TCP（`h2`）是 UDP（`h3`）不可用时的降级备选。
>
> 节点信息不采用签名保护，而是工作量以及与节点ID的绑定：
> - 承诺层：各字段经 Proof 绑定到 PeerID（见下），篡改即校验失败；
> - 声明层：ECHC 在连接时自验证，容忍 NATT/Extra 的篡改（类似无效IP）。
>
> 签名所能证明的“私钥持有”，在 TLS 连接时经 SPKIF 核对完成。
> 注意：中间人可将 ECHC 替换为无效配置以剥离 ECH 保护，客户端应对 ECH 协商失败的记录保持警惕。


### 字段分层与身份绑定

节点信息的字段分为两层：

- **承诺层**：版本、名识、协议、IP、SPKIF、时间戳。
  参与 Proof 的挑战种子计算（见下文），任何变更都会使 Proof 失效，连带影响 PeerID。
- **声明层**：端口、ECHC、NATT、Extra。
  不参与挑战种子计算，节点可持有同一 Proof 自由更新这些字段而保持身份不变。

节点身份ID是 `Proof` 的哈希摘要，迫使攻击者研磨 PeerID（逼近目标 StoreKey）时必须支付工作量成本。


### 身份关联与信誉锚点

PeerID 随承诺层字段的变更而更替（地址漂移、时间戳刷新等），它不是持久身份，也不适合作为信誉的锚点。

跨应用的身份关联由节点**自主选择**：

- 节点在各子网的 PeerID 不同（名识不同），若节点复用同一 SPKI，即可主动选择可关联。
- 节点为每个应用使用独立密钥，则各身份天然不可关联。

信誉系统应以 SPKIF 为锚点而非 PeerID，它不受地址漂移与时间戳更替的影响。普通用户节点默认隔离；基础设施运营者可通过密钥复用，自愿积累跨服务的信誉。


### 时间戳语义

- **名识记录（应用节点信息）**：发布时间仅供参考排序，记录的有效性以连接验证为准。
- **基网节点**：采用低频更新窗口，默认7天（可配置），过期记录被降权或弃用，节点应重新发布。
  适度的身份更替可迫使 Sybil 身份成为持续性成本（而非一次性）。


### 校验纪律与冲突处置

消费方收到节点信息后，必须按序执行：

1. 以承诺层字段重建挑战种子，验证 Proof 的 Equi-X 解合法；
2. 核对 `Hash256(Proof) == PeerID`；
3. 连接时核对对端证书 SPKI 与 SPKIF 一致。

记录在被成功连接验证之前均为**临时记录**。同一 PeerID 出现多份冲突记录时（攻击者可能拼接他人的合法 Proof 与有毒的声明层字段），以连接验证结果为准。



## 基础网络

基网采用 DHT（Kademlia）技术，通过节点ID（`PeerID`）创建结构化存储、查询和均衡的拓扑连接关系。

设置工作量约束，**Proof**采用抗 ASIC 矿机的 `Equi-X` 哈希算法，尽可能抑制攻击者快速创建 Sybil 虚假节点，大规模垄断任意目标位置。

```go
// 生成：
// @domainTag 固定的基网域标识
// @Ver 节点信息格式版本号
// @Proto 节点支持的协议（h3/h2）
// @AppID 名识（应用标识）
// @IP 节点公网 IP，IPv6 取 /64 前缀
// @SPKIF 可由节点自签名证书 SPKI 计算而来
// @Timestamp 节点信息发布时间（Unix 秒）
// @Rand16 一个16字节的随机数，将成为证明的后半段
// @solution 一个合法解，2*8 = 16字节
for {
    challengeSeed := Hash256( domainTag || Ver || Proto || AppID || IP || SPKIF || Timestamp || Rand16 )
    solution, err := equix.Solve(challengeSeed, Rand16[0])
}
Proof := solution || Rand16
PeerID := Hash256(Proof)

// 验证：
// 非对称代价，验证比创建轻量。
Rand16 := Proof[16:]
challengeSeed := Hash256( domainTag || Ver || Proto || AppID || IP || SPKIF || Timestamp || Rand16 )

solution := Proof[:16]
isValid := equix.Verify(challengeSeed, solution, Rand16[0])

isIdentity := Hash256(Proof) == PeerID
```

每一个节点存储与自己 PeerID 异或距离最近的节点集（基网节点），供其它节点查询和路由。同时，节点也存储名识（实为 `StoreKey`，见下文）与自己 PeerID 异或距离最近的节点集（应用节点），供任意节点查询其需要的应用。


### 名识的抗审查性

应用的名识通常是固定的，以便于识别查找，即便是多个，也有限度。因此审查者可以针对特定的敏感应用名识，创建与其距离临近的节点，垄断存储和检索（任意阻断或投毒）。

因此这里设计采用动态的 DHT 策略，名识的哈希指纹并不直接用于存储距离比较，而是用加入不可预知的随机数的存储键，算法如下：

```go
// 混合常数，增加Bit位复杂性（FxHash 算法常量）
Mix := 0x517cc1b727220a95
// 离散上限（不含）
// 不同应用根据自己的网络规模，设置不同上限值。
dispelMax := 256
// 离散因子，扩张名识键规模
RandX := rand.Intn(dispelMax) * Mix

// @Seed_e 由 drand 网络提供随机数。
// StoreKey 用于与节点ID比较异或距离
StoreKey := Hash256( Seed_e || 名识 || RandX )
```

- 名识记录（应用节点信息）存储在离 `StoreKey` 最近的节点上（Kademlia 路由方式不变）。
- 每过一段时间执行一次转储动作（分批转储，均衡全网负载），完成名识的存储位置重洗。
- 发布方、转储方、存储方与查询方独立计算同一 `StoreKey`，无需任何协调。

这样，审查者如果要屏蔽某名识应用，就需要不断跟进存储键的变化，相对于静态的 DHT 存储来说，这会使成本高出不少。

另外，名识记录的存储还支持*资格抽签*（VRF）的第二层防护，详见 [VRF周期重洗](VRF周期重洗.md) 相关部分。以及作为托底备选的*自由搜寻*方案（见下文）。


#### 关于离散因子

应用的名识相对固定，而一个节点存储该名识（Key）对应的节点信息（Value）的数量也有限，假设为*20*（可配置），那一个应用的入口节点就只有20个了。这显然不足。

加入一个小范围可变的离散因子，可以让名识键（StoreKey）多样化，从而增加存储者和入口节点信息的规模。此时最多可容纳 `256*20 = 5120` 条节点信息。

特定应用应当根据自身发展的规模，定义这个离散程度（dispelMax）：小网络有效节点少，离散程度就应该小，不然无效键较多（有键而无实际登记节点）。

> **实现：**
> 为避免审查者收集某应用的全部节点并封杀，Values 容量通常应配置得更高（如*40+*），
> 但是节点请求信息时，存储者并不会返回名识对应的全部节点信息，而是随机选取一部分（且可能含无效IP）。

**注意**：与常规数据的 `Key:Value` 不同，数据的哈希键是唯一的，但名识键对应的应当是一个值集，包含了属于该名识（应用）的不同节点，且这些节点是随机的，当它们注册时，被添加到属于该名识的值集里。也即，Key 对应的值并不是确定性的，Key 只是一个查询索引。


### 初始工作量认证

为提升连接成本，抑制攻击者发起大量连接，这里设计了工作量认证机制：

- 节点发起 TLS 连接请求，ClientHello 中即需要包含工作量证明。
- 接受连入的服务端验证工作量，如果合法，返回 ServerHello 包，携带自签名证书和首分享数据。
- 如果工作量验证失败，返回模拟浏览器的普通 ServerHello（包含CA证书链），或简单丢弃。

初始连接工作量认证详情请参阅文档 [工作量认证](工作量认证.md)。


### 暴力发现的可能

P2P世界中一个久未解决的难题，就是节点上线时的初始引导节点的中心化问题：引导节点一旦被封锁……

本设计有一个思考：*在不追求及时性的前提下，如果目标网络足够大，遍历全网IPv4地址，暴力发现初始的入口节点是否可行？*

在本设计中，基网是一个P2P世界的基础设施，如果大量的应用支持并加入进来，它们作为基网兼节点充实基网的规模……一个百万级连接的网络是可能的。在此规模下，暴力发现就有了可行性。

而且作为一种优化，历史IP可能是有用的：如果节点只是切换到了它附近的位置，以历史IP为原点的小范围搜寻会很高效。另外，固定活跃的IP子网也是一个可优化的方向。

> **提示：**
> 如果有必要，用户使用一台小设备挂机，持续探测……成本可能可接受。


### 关于无效IP

审查者也可以连入网络，然后收集节点并屏蔽。在无法区分IP实际指向的情况下，大量的无效节点可以加重审查者负担，而如果无效节点指向大平台IP，封杀更会造成附带伤害……这或许也可以抑制审查的力度。

无效节点信息来源于登记后下线但尚未移除的节点记录，或者用户主动配置的「毒IP」（大平台IP）。后者是客户端用户自主的选择，无法阻止，但这通常是由现实的严峻程度演生而来，不应该是常态。

无效IP混合在分享的节点清单里，对本网络不可用，但我们需要适度的容忍它们。

对无效IP的访问相当于可用性测试，如果对方不可用，就会放弃而不是持续地访问尝试，因此负面影响有限。


### 安全连接

由于P2P网络的节点间不需要信任对方，因此连接仅需采用安全连接（TLS），避免第三方的窥探和分析即可。证书采用自签名证书，验证采用 SPKI 指纹（Hash256(SPKI)）核对。

在应用子网内部，节点也会分享、扩散包含 SPKI 指纹在内的节点信息（同类扩散）。



## 节点发现

### DHT 结构化查询

这种搜寻有两种情况（各自独立）：

1. 搜寻节点ID与自己ID距离临近的同类节点（模糊查询），创建基础网络的均衡连接。
2. 按名识搜寻特定应用的节点（精准 Key:Values 查询），依然借助于异或距离结构化查询存储者。

这是基于 DHT 技术的结构化搜寻，高效且节省。

> **注意：**
> DHT 查询是询问者节点直接请求节点信息，自己提取并逐个尝试，循环迭代。而不是通过广播中转的方式。
> 在这种模式下，询问发起者掌握所有的主动权，逻辑也更简单。

对于第二种情况的搜寻，虽然采取了抗审查的动态 DHT 和适度扩散措施，但如果攻击者强大，依然可能是一个问题。因此，本设计还提供一个备选兜底方案——**自由搜寻**。


### 自由搜寻（按名识）

核心原理：*基于应用池节点信息的「随机扩散」，以及随机游走的微广播「风暴发现」*。


#### 节点信息的随机扩散

基网节点会存储向其注册的应用节点的信息，以名识为键并且随机分享。

与 DHT 结构化存储不同，此时无需采用动态存储键措施，按名识本身的哈希键存储/登记即可。

```go
Key := Hash256( domainTag || 名识 )
```

随机分享包括两个层级：对名识本身的分享；对该名识下节点信息集里成员的分享。都应是随机模式。

随着时间的推移，节点会在全网范围内自由扩散……这种扩散是随机的，扩散的效率（速度和均匀性）无法确定也无法预测。


#### 有限度的微广播风暴

自由搜寻基于查询广播，但转播的跳数极为有限：仅**2**跳转发，严格约束查询请求的放大影响。

- 查询请求的初始跳数为 `2`，每一次转播跳数减一，至跳数为 `0` 时不再转播。
- 中间转播者**不检查**自身是否满足查询条件，仅广播路径的末端节点检查自身存储，是否有目标名识的节点信息。
- 每一个查询请求都需要包含*工作量证明*，以抑制攻击者的垃圾查询风暴。
- 对于首跳接收者节点来说，同一查询者的请求频率最高为 `4s/次`。严格约束请求数量。
- 每次转发最多**8**个下级节点。每请求扩散率：`8*8 = 64`。
- 每个末端节点最多返回**8**条记录。全量回传，每请求响应记录最多：`64*8 = 512`。

工作量相关逻辑伪代码：

```go
// 生成：
// @domainTag 查询专用域标识
// @Addr1 首跳节点公网地址（IP:Port）
// @Nonce 首跳节点生成的随机数，作为挑战种子
// @Rand16 运算者寻找的16字节随机数，会作为证明的后半段
// @solution 一个合法解，2*8 = 16字节
for {
    challengeSeed := Hash256( domainTag || Addr1 || Nonce || Rand16 )
    solution, err := equix.Solve(challengeSeed, Rand16[0])
}
Proof := solution || Rand16

// 验证：
// - 首跳节点验证：自己知道 Addr1 和 Nonce
// - 次跳节点验证：Nonce 由首跳节点提供，Addr1 为对端地址
// - 末端节点：无需验证，直接执行查询。
Rand16 := Proof[16:]
challengeSeed := Hash256( domainTag || Addr1 || Nonce || Rand16 )

solution := Proof[:16]
isValid := equix.Verify(challengeSeed, solution, Rand16[0])
```

这里，中间转播者仅负责验证工作量并转发请求，最大化末端规模。


#### 随机游走的风暴发现

存储是自由的，末端节点未必支持查询的目标名识，因此没有节点信息返回。查询者通常需要不断迭代，并且不断更新所连接的节点，一轮又一轮……

如果末端节点存储的节点信息总共为**4k**（4096），按照上面的广播扩散模型：`64*4096 = 262144`，每一个请求可以触及 26 万个节点信息。

如果一个查询者平均连接**8**个节点，一轮请求即可触及（筛选）`262144*8 = 2097152` 约 200 万个节点。当然，这种触及会有大量重复，但好像也还不错。

> **提示：**
> 小众应用节点数量不多（可见性不足），查询通常需要更多的时间。


### 自由搜寻规范

#### 搜寻请求

搜寻请求包称为*询问包*，含如下内容。

> **注：**
> 下面的伪代码中：`[n]` 表示Bit位数，`(n)` 表示字节数，`(~)` 表示变长字节数。

```go
(2)     Ver:        版本号。
(8)     ID:         标识本次询问，用于回复包中对应其源请求。
(8)     Timestamp:  询问时间戳（Unix，毫秒）。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(32)    Key:        目标名识键。
(32)    Proof:      工作量证明
[4]     Hops:       剩余跳数，初始值2，最低到0。
[4]     ECDHE：     临时密钥协商算法。
(~)     Share:      密钥协商算法相应的数据（如公钥）。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     Extra：     可选，灵活空间，≤64 字节。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
```


#### 回应消息

回应的消息称为**回复包**，结构如下：

```go
(2)     Ver：       版本号。
(8)     ID：        原询问包中的ID，用于上级对应请求源。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     Exchange：  应答者密钥协商数据，算法与询问包相同。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
注：以下信息已用共享密钥加密
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(8)     Timestamp:  回复时间戳（Unix，毫秒）。
(32)    Key:        目标名识键，与询问包内的同字段值相同，用于核实确认。
(~)     Nodes:      分享的节点信息集。不超过8个节点。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
(~)     Extra:      可选，可能需要的附加信息，≤64 字节。
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
```



## 应用池

应用池是不同名识对应的节点集合的总集，包括通过 DHT 查询和自由搜寻两条路径发现，都有各自的节点池集合（应用池）。

基网节点应当都是 NATT 可直连的 `Public` 或 `FullC` 类型，但应用池节点可以不必如此，如果应用节点是 NATT 不可直连但可打洞类型（`RC`, `P-RC`），记录也是应该的。查询者找到这些节点，得到它们的 PeerID，然后就可以在 STUN 服务子网上去找它们，最后通过 STUN 服务节点提供的信令中介完成打洞互连。

> **提示：**
> 同一应用的节点间没有任何关联，通过 PeerID 找到的 STUN 服务节点也各异，
> 因此审查者很难通过集中封锁/攻击某个 STUN 服务节点来阻止某一应用的节点间互连。


### 稀疏性策略

> **注意：**
> 仅适用于自由搜寻模式下，应用池节点信息分享场景。不用于应用节点自主登记注册时。
> 因为应用节点自主登记时，有其它安全措施约束。

节点池中的IP应当遵循**稀疏性**原则，即各个IP之间有适当的距离，避免被攻击者集中注入不良节点信息。

当节点接收对端分享的节点信息时，需要以当前候选池的节点IP序列为基础，过滤/挑选分享过来的节点信息。这样，攻击者通过分享注入不良节点群的企图就会失去确定性——它们无法预知对端当前的节点池状况，进而组织有效的IP集。

> **分享频率：**
> 节点需要对同一请求者限制节点分享的次数和数量，避免攻击者探测自身节点池状况。

稀疏性策略用不确定性对抗攻击者IP注入，不过这只是一种缓解措施，攻击危害依然存在。

> **算法：**
> 将IP转换为整数，计算两个整数的差值。分 IPv4 和 IPv6 两个等级。
> 池中原有的IP不可移除，在一个有序的值集中，新IP只能插入，且需满足前后的距离约束。
>
> 节点池中原有的IP间可能不满足距离要求，那是节点自主登记插入的结果，不影响。

客观地来看，大网段可以容忍较多的相同子网IP，而小网段容忍的同子网IP就会较少。如果必要，可以分网段设置不同的距离约束。



## 安全风险

本网络的目标是尽可能协助应用发现节点，不提供节点本身的可信保证。

应用需要自行验证节点是否可信，或者可以脱离信任（比如文件分享P2P应用，是以数据指纹来保证文件的可靠性，而非信任分享者）。


### Sybil女巫攻击

**风险：** 攻击者创建大量虚假节点占据网络。
**对策：**
- 节点连入时，需要提供初始的工作量认证。
- 节点创建身份，也需要提供工作量证明（节点信息.Proof，与IP关联）。
- 节点信誉系统（新节点权重低。信誉以 SPKIF 为锚点，支持跨应用自主选择关联）。
- IP分布检测（同一IP段节点数限制）。


### 日蚀攻击

**风险：** 攻击者隔离目标节点，使其只连接到恶意节点
**对策：**
- 节点公网池多样性(不同IP段、不同地区)。
- 随机连接策略。
- 定期刷新连接。


### DDoS放大攻击

**风险：** 搜寻机制被用于DDoS放大攻击
**对策：**
- 尽可能少的转播跳数（严格2次转播，共3级）。
- 节点搜寻只是为了找到入口，无需高频，因此搜寻速率受到严格限制（*4s/次*）。
- 同一查询请求，不会重复转播。**重复性判断**：`ID + 时间戳 + 目标名识键` 对比，时间窗口为**5**分钟。
- 超出时间窗口的请求不会转发，时间窗口 **5** 分钟（可配置）。
- 每一个新的查询都需要工作量证明，提升大批量查询成本。


### 流量分析攻击

**风险：** 攻击者通过流量模式识别网络
**对策：**
- 伪装成浏览器发送 HTTP/2（TCP）或 HTTP/3（UDP）连接请求。
- 默认支持 ECH（Encrypted Client Hello）。
- 初始连接的工作量认证（CH.random）无特征，虽然可验证性分析，但仅能海量中随机抽查。
- 无 ECH 时 ClientHello.SNI 格式合法且非敏感。


### 资源耗竭攻击

**风险：** 恶意节点大量消耗网络资源
**对策：**
- 连接数限制（每节点最大连接数）。
- 带宽限制（每连接最大带宽）。
- 请求频率限制（防止请求洪泛），参考「DDoS放大攻击」防范对策。
- 快速隔离机制（异常节点快速封禁）。
- 每一个请求都需要工作量证明，对挖攻击者能力。



## 其它事项

### 初始节点植入

初始节点可以由应用内置或用户配置导入。如果两种方式都失效，则采用暴力发现的方式遍历IPv4地址进行搜寻。

在网络发展的初期，基网的规模不大，在App中预先植入一些已知的基网节点是必要的。当网络发展至一定规模，暴力发现的成本不高之后，这些预先植入的节点信息（可以保留）就无关紧要了。


### 被动分享

节点不应当主动分享自身存储的节点信息，而应该在对方请求后才提供。这更简单也更合理。

客户端在连入服务器时，服务器会在TLS握手回应中附带一批节点信息（首分享）。这既是客户端连入请求的默认逻辑，也强化了节点信息扩散的鲁棒性。


### 关于服务子网

服务子网是一些公共的服务，比如 STUN 探测和打洞服务、数据中转服务等。它们由单独的项目创建，这里无需涉及。

> **提示：**
> NAT 内网节点间的互连通过 STUN 服务子网提供打洞服务。项目详见 [cxio/stun2p](github.com/cxio/stun2p)。



## 技术栈

- **UDP**：采用 QUIC/HTTP3 作为主要的通讯方式。
- **TCP**：适用于 UDP 受限的网络环境，降级采用 HTTP/2 协议，也可与 HTTP3 同时运行（由配置启用）。
- **加密**：采用 TLS v1.3 安全传输协议，支持后量子加密算法（如 X25519MLKEM768）。
- **消息格式**：采用 Protobuf 进行消息序列化和反序列化。
- **语言**：使用 Go 语言实现，充分利用并发能力。



## 项目边界

- NAT 内网节点的 NAT 类型判断由项目 `github.com/cxio/stun2` 库支持。
- NAT 内网节点间的连接协助由项目 `github.com/cxio/stun2p`（服务子网）负责。
- ClientHello 和 ServerHello 的工作量支持由项目 `github.com/cxio/wtls` 库实现。



## 附：名词解释

### 基网纯节点

仅实现基网本身的功能，没有任何其它用途的节点，称为基网的**纯节点**。

它们是基网初期扩展的基础（通常成本低廉），同时也可能是未来远期整网的融洽成份（或许会有某些必要的进一步工作）。


### 基网兼节点

连入基网的应用节点，它们是基网的重要组成部分，不过有*兼职*的观感。

兼职基网并不会占用多少资源。所以一个应用节点如果从基网获得了需要的入口（理论上就可以脱离基网了），但还是希望继续保持连接，只有这样才能极大扩展基网的规模，从而让无中心的暴力发现成为可能。

兼节点不可或缺！它们是基网百万级以上规模的关键力量。


### 自由市场

所有参与基网连接的节点的集合（基网纯节点+任意子网节点），统称为节点的*自由市场*。

这只是一种逻辑上的称谓，便于表达，不是另有一个独立实体。**基网**的逻辑不包含应用子网其自身的功能部分。

自由市场的持续增长可能带来真正的去中心化：完全的无中心，以至于不需要预置的初始引导节点。
